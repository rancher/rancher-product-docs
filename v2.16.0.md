# Release v2.16.0

> [!IMPORTANT]
> - If you are using Active Directory Federation Service (AD FS), upgrading to Rancher v2.10.1 or later may cause issues with authentication, requiring manual intervention. These issues are due to the AD FS Relying Party Trust not being able to pick up a signature verification certificate from the metadata. For more information, see [\#48655](https://github.com/rancher/rancher/issues/48655). These issues can be corrected by either of two methods:
>
>   - Updating the Relying Party Trust information from federation metadata (Relying Party Trust → Update from Federation Metadata…​).
>
>   - Directly adding the certificate (Relying Party Trust → Properties → Signature tab → Add → Select the certificate).

Rancher Community v2.16.0 is the latest minor release. This is a Community version release that introduces new features, enhancements, and various updates.

## What’s New - v2.16.0

### Kubernetes support and lifecycle updates

- Rancher v2.16 adds support for Kubernetes v1.37. It removes support for Kubernetes v1.34.

- **Production image update:** Production installations now use the `rancher/rancher-server` image. The `rancher/rancher` image remains for single-node Docker installations.

### Cluster provisioning highlights

- **CAPI resource sharing:** You can share ConfigMaps and Secrets with CAPI clusters using the `rke.cattle.io/object-authorized-for-clusters-selector` annotation.

- **GKE release channels:** You must select a release channel when provisioning a GKE cluster. Regular is the default channel.

### Authentication highlights

- **Generic SAML provider:** Rancher introduces a configurable Generic SAML provider. This supports SAML-compliant identity providers.

- **Independent token TTLs:** You can configure default and maximum time-to-live (TTL) values independently for authentication and kubeconfig tokens.

### Dashboard highlights

- **Configurable table views:** Rancher Dashboard supports configurable views for core tables. You can filter, save, share, publish, and export these views.

- **Workloads overview search:** The Workloads Overview page includes a cross-resource search function. This search respects namespace filters and list permissions.

### CLI highlights

- **New experimental Rancher CLI:** The new Rancher CLI is available as an experimental release. Note commands, flags, and output can change between releases. The CLI is released separately from Rancher and supports Rancher v2.14 and later. It provides a structured, AI-native command-line interface with programmatic JSON/YAML output. It includes explicit dry-run and apply safety controls. The legacy CLI is now deprecated. See the [Rancher CLI documentation](https://ranchermanager.docs.rancher.com/v2.16/cli/rancher-cli) for setup and migration details.

## Rancher General

### Major Bug Fixes

- Rancher settings that use environment-based defaults can now be changed through the UI or API when those settings are user-configurable. The published environment variables and Helm chart mappings remain unchanged. See [\#56307](https://github.com/rancher/rancher/issues/56307).

## Cluster Provisioning

### Features and Enhancements

- Rancher now supports for Kubernetes v1.37. See [\#55781](https://github.com/rancher/rancher/issues/55781) for information on Rancher support for Kubernetes v1.37. You can view the [upstream Kubernetes changelog](https://github.com/kubernetes/kubernetes/blob/master/CHANGELOG/CHANGELOG-1.37.md) for v1.37 for a complete list of changes.

- **Expanded permissions for the `user` role**: The built-in `user` role grants `get` and `list` permissions for namespaced `capiproviders` resources in the `turtles-capi.cattle.io` API group, allowing standard users to view existing provider configurations. Because users with these permissions can view `.spec.variables` in plain text, store credentials and sensitive data in `.spec.credentials` instead. For more information, see [Rancher Turtles CAPI Provider reference](https://turtles.docs.rancher.com/turtles/stable/en/reference/capiprovider.html) and [\#58389](https://github.com/rancher/rancher/issues/58389).

- **Expanded permissions for the `clusters-create` role**: The built-in `clusters-create` role grants `get` and `list` permissions for namespaced `capiproviders` resources in the `turtles-capi.cattle.io` API group, allowing cluster creators to view existing provider configurations. Because users with these permissions can read `.spec.variables` in plain text, store credentials and sensitive data in `.spec.credentials` instead. For more information, see [Rancher Turtles CAPI Provider reference](https://turtles.docs.rancher.com/turtles/stable/en/reference/capiprovider.html). See [\#55167](https://github.com/rancher/rancher/issues/55167).

- **Label-based sharing for `machineSelectorFiles` sources**: You can now add the `rke.cattle.io/object-authorized-for-clusters-selector` annotation to share `secret` and `ConfigMap` resources with clusters by label. The annotation accepts a Kubernetes label selector and delivers the resource to clusters in the same namespace with matching labels. An empty selector value matches all clusters in the namespace, while an invalid selector matches none. The existing `rke.cattle.io/object-authorized-for-clusters` annotation continues to work as before. For more information, see [\#47438](https://github.com/rancher/rancher/issues/47438).

- When provisioning a GKE cluster, you must select a release channel: Rapid, Regular, Stable, or Extended. Regular is the default. See [\#56879](https://github.com/rancher/rancher/issues/56879).

### Behavior Changes

- Rancher v2.16 no longer supports Kubernetes v1.34. See [\#57345](https://github.com/rancher/rancher/issues/57345).

- The Linode node driver is now URL-based and is disabled by default on new installations. Existing Linode clusters continue to use the driver after an upgrade. See [\#54574](https://github.com/rancher/rancher/issues/54574).

- The webhook requires `GET` permission on each `secret` or `ConfigMap` referenced by `machineSelectorFiles`. This check occurs when you add or modify an entry, create a cluster, or update labels on a cluster that matches a selector annotation. Before adding `rke.cattle.io/object-authorized-for-clusters-selector` to an existing `secret` or `ConfigMap`, verify which clusters reference it. Removing an annotation stops future deliveries, but it does not delete files already written to cluster nodes. To prevent a cluster from receiving further updates from a `secret` or `ConfigMap`:

  1.  Remove the cluster from `rke.cattle.io/object-authorized-for-clusters` and ensure its labels no longer match `rke.cattle.io/object-authorized-for-clusters-selector` (or remove the entry from `machineSelectorFiles`).

  2.  Rotate the contents of the `secret` or `ConfigMap` if the cluster already received the previous values.

      For more information, see [\#47438](https://github.com/rancher/rancher/issues/47438).

## Rancher App (Global UI)

### Features and Enhancements

- Rancher Dashboard now supports configurable views for core tables. You can filter, save, share, publish, and export table views. Published views are readable by users who can access `tableconfiguration.ui.cattle.io` and can reveal resource or namespace names. UI extensions do not enable configurable tables by default. Extension developers can enable them by setting `:table-views="true"` on `ResourceTable` components. The feature uses the enabled-by-default `ui-configurable-tables` feature flag. See [\#18745](https://github.com/rancher/dashboard/issues/18745).

- The Workload Overview page now includes a search that finds workloads across resource types by partial name. Search results respect namespace filters and list permissions. See [\#18232](https://github.com/rancher/dashboard/issues/18232).

### Major Bug Fixes

- The GKE provisioning UI now offers only Kubernetes versions supported by a release channel. See [\#18927](https://github.com/rancher/dashboard/issues/18927).

### Behavior Changes

- Server-side pagination, its supporting API, and the SQLite cache are now always enabled. The `ui-sql-cache` feature flag and the Rancher CLI `--sql-cache` flag are removed. For more information, including disk space requirements, see the [UI Server-Side Pagination](https://ranchermanager.docs.rancher.com/v2.16/how-to-guides/advanced-user-guides/ui-server-side-pagination) documentation. See [\#15546](https://github.com/rancher/dashboard/issues/15546), [\#53985](https://github.com/rancher/rancher/issues/53985), and [\#53996](https://github.com/rancher/rancher/issues/53996).

### Known Issues

- When adding a repository, the `Repositories` list shows `Active` immediately instead of `In Progress` while the repository is downloading. See [\#56747](https://github.com/rancher/rancher/issues/56747).

- The Rancher command-line interface now supports both legacy v3 tokens and `ext.cattle.io/v1` tokens. See [\#55988](https://github.com/rancher/rancher/issues/55988).

### Major Bug Fixes

- Rancher fixed an authorization issue that could allow users without sufficient local-cluster permissions to access shell endpoints. See [CVE-2026-104623](https://github.com/rancher/rancher/security/advisories/GHSA-8x6f-2v58-x6p7).

## Role-Based Access Control (RBAC)

### Features and Enhancements

- Project Owners and Members can manage Gateway API, Istio, and Traefik resources with their default permissions. See [\#55638](https://github.com/rancher/rancher/issues/55638) and [\#56008](https://github.com/rancher/rancher/issues/56008).

- When you enable the `roletemplate-aggregation` feature flag, you can use the `ClusterScopedRules` field in a project `RoleTemplate` to grant cluster-scoped permissions. This field replaces promoted rules, which grant implicit cluster-scoped access to a fixed set of resources. Both mechanisms are supported. For more information, see [RoleTemplate aggregation](rancher-admin/experimental-features/role-template-aggregation.xml) and [\#56306](https://github.com/rancher/rancher/issues/56306).

- The built-in standard user role can view node metrics. See [\#45849](https://github.com/rancher/rancher/issues/45849).

## Backup/Restore

### Features and Enhancements

- Rancher Backup and Restore now includes additional CAPI resources in its resource set adding support for configurations that include Rancher Turtles CAPI Native and CAPI Plug and Play (PnP) downstream clusters. However, certain caveats and limitations apply. For more information, see the [documentation](https://ranchermanager.docs.rancher.com/v2.16/how-to-guides/new-user-guides/backup-restore-and-disaster-recovery/back-up-restore-usage-guide#_capi_provider_resources), [\#56874](https://github.com/rancher/rancher/issues/56874), and [\#54990](https://github.com/rancher/rancher/issues/54990).

## Install/Upgrade Notes

If you’re installing Rancher for the first time, your environment must fulfill the [installation requirements](https://ranchermanager.docs.rancher.com/v2.16/getting-started/installation-and-upgrade/installation-requirements).

> [!IMPORTANT]
> - Rancher now requires the cluster it runs on to have the [Kubernetes API Aggregation Layer](https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/apiserver-aggregation/) enabled. This is because Rancher extends Kubernetes with additional APIs by registering its own extension API server. Please note that all versions of Kubernetes supported in this Rancher versions K8s distributions (RKE2/K3s) will have the aggregation layer configured and enabled by default.
>
>   - Refer to the [Extension API Server documentation](https://ranchermanager.docs.rancher.com/v2.16/api/extension-apiserver#aggregation-layer-is-required) and [\#50400](https://github.com/rancher/rancher/issues/50400) for more information.
>
> - Rancher Kubernetes Engine (RKE/RKE1) has reached end of life as of **July 31, 2025**. Rancher versions 2.12.0 and later no longer support provisioning or managing downstream RKE1 clusters. We recommend replatforming RKE1 clusters to RKE2 to ensure continued support and security updates. Learn more about the transition [here](https://www.suse.com/support/kb/doc/?id=000021518).
>
>   - Rancher now has a pre-upgrade validation check for RKE1 resources which fails and lists the RKE1 resources if present. Refer to [\#50286](https://github.com/rancher/rancher/issues/50286) for more information.
>
> - It is crucial that you review the available disk space on your nodes and plan accordingly before upgrading to Rancher v2.12.0 and later to avoid potential disk pressure and pod eviction issues.
>
>   - For additional information, refer to the [UI Server Side Pagination - Disk Space documentation](https://ranchermanager.docs.rancher.com/v2.16/how-to-guides/advanced-user-guides/ui-server-side-pagination#disk-space).
>
> - Rancher now has an enablement option called [`AUDIT_LOG_ENABLED`](https://ranchermanager.docs.rancher.com/v2.16/how-to-guides/advanced-user-guides/enable-api-audit-log#viewing-api-audit-logs:~:text=Description-,AUDIT_LOG_ENABLED,-false%20%2D%20Disables%20the) for API Audit Logs for a Rancher installation.
>
>   - In Rancher versions 2.11.x and earlier, only the `AUDIT_LEVEL` could be set and the default log level (`0`) would disable the audit log. In Rancher versions 2.12.x and later, the default log level (`0`) now only contains the log request and response metadata, and can be set when configuring `AUDIT_LOG_ENABLED`. If installing or upgrading via Helm you can enable the API Audit Logs and specify the log level by applying the following setting to your Helm command: `--set auditLog.enabled=true --set auditLog.level=0`. See the [Enabling the API Audit Log to Record System Events](https://ranchermanager.docs.rancher.com/v2.16/how-to-guides/advanced-user-guides/enable-api-audit-log) documentation and [\#48941](https://github.com/rancher/rancher/issues/48941).

## Changes in Image Artifacts

- Rancher now uses the `rancher/rancher-server` image for production installations. The `rancher/rancher` image remains available for single-node Docker installations, and the Rancher Helm chart now uses the server image. See [\#57653](https://github.com/rancher/rancher/issues/57653) and [\#57434](https://github.com/rancher/rancher/pull/57434).

Image artifact digests are renamed in Rancher v2.12.0, v2.11.4 and v2.10.8. Up until this change, separate image digests files for each operating system and architecture have been maintained for compatibility reasons. With this change, only one file for each operating system is to be provided:

- The `rancher-images-digests-linux-amd64.txt` and `rancher-images-digests-linux-arm64.txt` files are to be renamed to `rancher-images-digests-linux.txt`.

- The `rancher-images-digests-windows-ltsc2019.txt` and `rancher-images-digests-windows-ltsc2022.txt` files are to be renamed to `rancher-images-digests-windows.txt`.

## Upgrade Requirements

- **Creating backups:** [Create a backup](https://ranchermanager.docs.rancher.com/v2.16/how-to-guides/new-user-guides/backup-restore-and-disaster-recovery/back-up-rancher) before you upgrade Rancher. To roll back Rancher after an upgrade, you must first back up and restore Rancher to the previous Rancher version. Because Rancher will be restored to the same state as when the backup was created, any changes post-upgrade will not be included after the restore.

- **Helm version requirements:**

  - To manage Rancher 2.12.x and later, you must upgrade your Helm client to version 3.18 or newer.

  - This change is required to reflect the addition of Kubernetes 1.33 support with this release.

  - Currently, the official [Helm Version Support Policy](https://helm.sh/docs/topics/version_skew/) dictates that only Helm 3.18 supports the proper Kubernetes version range for Rancher 2.12.

- **CNI requirements:**

  - For Kubernetes v1.19 and later, disable firewalld as it’s incompatible with various CNI plugins. See [\#28840](https://github.com/rancher/rancher/issues/28840).

  - When upgrading or installing a Linux distribution that uses nf_tables as the backend packet filter, such as SLES 15, RHEL 8, Ubuntu 20.10, Debian 10, or later, upgrade to RKE v1.19.2 or later to get Flannel v0.13.0. Flannel v0.13.0 supports nf_tables. See Flannel [\#1317](https://github.com/flannel-io/flannel/issues/1317).

- **Requirements for air-gapped environments:**

  - When using a proxy in front of an air-gapped Rancher instance, you must pass additional parameters to `NO_PROXY`. See the [documentation](https://ranchermanager.docs.rancher.com/v2.16/getting-started/installation-and-upgrade/other-installation-methods/rancher-behind-an-http-proxy/install-rancher) and issue [\#2725](https://github.com/rancher/docs/issues/2725#issuecomment-702454584).

  - When installing Rancher with Docker in an air-gapped environment, you must supply a custom `registries.yaml` file to the `docker run` command, as shown in the [K3s documentation](https://docs.k3s.io/installation/private-registry). If the registry has certificates, then you’ll also need to supply those. See [\#28969](https://github.com/rancher/rancher/issues/28969#issuecomment-694474229).

In Rancher v2.6.0 and later, in the **Apps & Marketplace** UI, many Rancher Helm charts are named with a major version that starts with *100*. ## Long-standing Known Issues

### Long-standing Known Issues - Cluster Provisioning

- **Rancher v2.15.0:**

  - Imported clusters cannot reconnect to Rancher if their registration token is rotated while they are disconnected and the grace period ends before they reconnect. The cluster agent logs `400 Bad Request` with the response body `cluster not found`. As a workaround, re-run the registration command from the cluster **Registration** tab on the downstream cluster. To prevent the issue, increase the `crt-default-grace-period-minutes` setting to cover the expected downtime, or disable the `crt-token-ttl-rotation` feature flag. See [\#57078](https://github.com/rancher/rancher/issues/57078).

- **Rancher v2.14.0:**

  - Upgrading from Rancher v2.13.x to v2.14 or v2.15 leaves the old `rke2-machineconfig-cleanup` CronJob, ServiceAccount, and ConfigMap in `fleet-default`. Rancher also creates these resources in `fleet-local`, leaving two CronJobs with the same name. The old CronJob uses the v2.13.x agent image, contains a copy of the local cluster registration token, and runs without permissions. To work around this issue, verify each old object has the annotation `objectset.rio.cattle.io/id=rke2-machine-config-cleanup`. Then delete the old CronJob, ServiceAccount, and ConfigMap from `fleet-default`. Do not delete the shared ClusterRole or ClusterRoleBinding because the `fleet-local` CronJob uses them. See [\#58290](https://github.com/rancher/rancher/issues/58290). A backport to v2.16.1 was requested in [\#58290](https://github.com/rancher/rancher/issues/58290#issuecomment-6531972294).

- Not all cluster tools can be installed on a hardened cluster.

- **Rancher v2.8.1:**

  - When you attempt to register a new etcd/controlplane node in a CAPR-managed cluster after a failed etcd snapshot restoration, the node can become stuck in a perpetual paused state, displaying the error message `[ERROR] 000 received while downloading Rancher connection information. Sleeping for 5 seconds and trying again`. As a workaround, you can unpause the cluster by running `kubectl edit clusters.cluster clustername -n fleet-default` and set `spec.unpaused` to `false`. See [\#43735](https://github.com/rancher/rancher/issues/43735).

### Long-standing Known Issues - RKE2 Provisioning

- **Rancher v2.7.7:**

  - Due to the backoff logic in various components, downstream provisioned K3s and RKE2 clusters may take longer to re-achieve **Active** status after a migration. If you see that a downstream cluster is still updating or in an error state immediately after a migration, please let it attempt to resolve itself. This might take up to an hour to complete. See [\#42834](https://github.com/rancher/rancher/issues/42834).

- **Rancher v2.7.6:**

  - Provisioning RKE2/K3s clusters with added (not built-in) custom node drivers causes provisioning to fail. As a workaround, [fix](https://github.com/rancher/rancher/issues/37074#issuecomment-1664722305) the added node drivers after activating. See [\#37074](https://github.com/rancher/rancher/issues/37074).

### Long-standing Known Issues - K3s Provisioning

- **Rancher v2.7.6:**

  - Provisioning RKE2/K3s clusters with added (not built-in) custom node drivers causes provisioning to fail. As a workaround, [fix](https://github.com/rancher/rancher/issues/37074#issuecomment-1664722305) the added node drivers after activating. See [\#37074](https://github.com/rancher/rancher/issues/37074).

- **Rancher v2.7.2:**

### Long-standing Known Issues - Rancher App (Global UI)

Inputting a zero minimum node count through the UI can cause cluster creation to fail due to an invalid parameter error. To prevent this error from occurring, enter a minimum node count at least equal to the node count. See [\#11922](https://github.com/rancher/dashboard/issues/11922).

- **Rancher v2.7.7:**

### Long-standing Known Issues - Authentication

- **Rancher v2.9.0:**

  - There are some known issues with the OpenID Connect provider support:

    - When the generic OIDC auth provider is enabled, and you attempt to add auth provider users to a cluster or project, users are not populated in the dropdown search bar. This is expected behavior as the OIDC auth provider alone is not searchable. See [\#46104](https://github.com/rancher/rancher/issues/46104).

    - When the generic OIDC auth provider is enabled, auth provider users that are added to a cluster/project by their username are not able to access resources upon logging in. A user will only have access to resources upon login if the user is added by their userID. See [\#46105](https://github.com/rancher/rancher/issues/46105).

    - When the generic OIDC auth provider is enabled and an auth provider user in a nested group is logged into Rancher, the user will see the following error when they attempt to create a Project: `projectroletemplatebindings.management.cattle.io is forbidden: User "u-gcxatwsnku" cannot create resource "projectroletemplatebindings" in API group "management.cattle.io" in the namespace "p-9t5pg"`. However, the project is still created. See [\#46106](https://github.com/rancher/rancher/issues/46106).

### Long-standing Known Issues - Rancher Webhook

- **Rancher v2.7.2:**

  - A webhook is installed in all downstream clusters. There are several issues that users may encounter with this functionality:

    - If you rollback from a version of Rancher v2.7.2 or later, to a Rancher version earlier than v2.7.2, the webhooks will remain in downstream clusters. Since the webhook is designed to be 1:1 compatible with specific versions of Rancher, this can cause unexpected behaviors to occur downstream. The Rancher team has developed a [script](https://github.com/rancher/webhook/wiki/Remove-Webhook-from-downstream-clusters) which should be used after rollback is complete (meaning after a Rancher version earlier than v2.7.2 is running). This removes the webhook from affected downstream clusters. See [\#40816](https://github.com/rancher/rancher/issues/40816).

### Long-standing Known Issues - Virtualization Management (Harvester)

- **Rancher v2.13.1:**

  - When upgrading to Rancher v2.13.1 or higher while using Harvester v1.6.1, users may encounter an issue with their Load Balancers in downstream clusters using the Harvester Cloud Provider, and must perform the following [workaround](https://docs.harvesterhci.io/latest/troubleshooting/rancher#guest-cluster-loadbalancer-ip-is-not-reachable) to instruct Calico to not use any of the IP/interface managed by `kube-vip`. See [\#9767](https://github.com/harvester/harvester/issues/9767).

- **Rancher v2.7.2:**

  - If you’re using Rancher v2.7.2 with Harvester v1.1.1 clusters, you won’t be able to select the Harvester cloud provider when deploying or updating guest clusters. The [Harvester release notes](https://github.com/harvester/release-notes/blob/main/v1.1.2.md#important-information-about-rancher-support) contain instructions on how to resolve this. See [\#3750](https://github.com/harvester/harvester/issues/3750).

### Long-standing Known Issues - Backup/Restore

- When migrating to a cluster with the Rancher Backup feature, the server-url cannot be changed to a different location. It must continue to use the same URL.

- **Rancher v2.13.0:**

  - When performing a rollback from Rancher v2.13.0 to v2.12.3 using the backup and restore operator (BRO), the restore does not complete successfully. See [\#844](https://github.com/rancher/backup-restore-operator/issues/844). To work around this issue, you must scale down your Rancher deployment and uninstall the Webhook chart before performing the restore. For details, refer to this [Knowledge Base article](https://support.scc.suse.com/s/kb/Rolling-back-from-Rancher-v2-13-0-to-v2-12-3?language=en_US).

- **Rancher v2.7.7:**

  - Due to the backoff logic in various components, downstream provisioned K3s and RKE2 clusters may take longer to re-achieve **Active** status after a migration. If you see that a downstream cluster is still updating or in an error state immediately after a migration, please let it attempt to resolve itself. This might take up to an hour to complete. See [\#42834](https://github.com/rancher/rancher/issues/42834).
