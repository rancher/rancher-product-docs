This page outlines how to roll back Rancher to a previous version after an upgrade.

include::shared:ROOT:partial$en/rollback-warning.adoc[]

Follow the instructions from this page when:

* The running Rancher instance has been upgraded to a newer version after the backup was made.
* The upstream (local) cluster is the same as where the backup was made.

[TIP]
====
* Follow these steps to {xref-migrate-cluster}[migrate Rancher].
* If you need to restore Rancher to its previous state at the same Rancher version, see the {xref-rancher-restore}[restore documentation].
====

To roll back Rancher to a lower/previous version, use the *Rancher Backups* application and restore Rancher from backup.

Rancher has to be started with the lower/previous version after a rollback.

A restore is performed by creating a Restore custom resource.

[#_prerequisites]
== Prerequisites

Before initiating the rollback, verify the backup application and record the details of the backup you intend to restore. Because scaling down Rancher in <<_step_1_scale_down_the_rancher_deployment_to_zero_replicas,Step 1>> will make the Rancher UI inaccessible, perform these checks beforehand.

. Verify Rancher Backups is Installed:
  * Click *☰ > Cluster Management > local > Explore*.
  * In the left navigation bar, verify that *Rancher Backups* is present.
  * If the Rancher Backups app is not visible, you will need to install it from the Charts page in *Apps*. Refer {xref-helm-charts-in-rancher}#_access_charts[here] for more information.
. Record Backup Information:
  * Go to *Rancher Backups > Backups* and identify the backup you wish to restore.
  * Note the exact backup file name, storage location details (bucket name, folder, region, endpoint), and any associated secret names (e.g., encryption configuration secret or S3 credentials secret). You will need these to construct the Restore custom resource in <<_step_2_create_the_restore_custom_resource,Step 2>>.
  * CLI Alternative: If the Rancher UI is already inaccessible, retrieve existing backups via `kubectl`:
+
[,shell]
----
kubectl get backups.resources.cattle.io -A
----


[#_step_1_scale_down_the_rancher_deployment_to_zero_replicas]
== Step 1: Scale down the Rancher Deployment to zero replicas

Before performing the restore, manually scale the Rancher deployment to zero replicas.

[WARNING]
====
Scaling down the Rancher Deployment is a required step to ensure successful rollback. The *Rancher Backups* application is used to backup and restore Rancher state, but does not itself alter the version of the Rancher Deployment. Whilst it scales the Rancher Deployment down to zero replicas to perform a restore operation, it will scale the Deployment up to the previously running number of replicas upon completion of the restore. As a result, where Rancher is not first manually scaled to zero replicas, before initiating the restore in <<_step_2_create_the_restore_custom_resource,Step 2>>, it is possible that Rancher Pods - running the upgraded Rancher version - start after the restore operation, but before the Rancher release is rolled back to the previous version in <<_step_3_roll_back_to_a_previous_rancher_version,Step 3>>.
====

Run the following command against the local cluster:
[,shell]
----
kubectl -n cattle-system scale deployment rancher --replicas=0
----

Verify that all Rancher pods have terminated:
[,shell]
----
kubectl -n cattle-system get pods -l app=rancher
----

[#_step_2_create_the_restore_custom_resource]
== Step 2: Create the Restore Custom Resource

Because the Rancher UI is unavailable after scaling down the Rancher deployment in <<_step_1_scale_down_the_rancher_deployment_to_zero_replicas,Step 1>>, the `Restore` custom resource must be created using the `kubectl` CLI.

. Create a file named `restore.yaml` containing your `Restore` configuration using the backup details noted in the <<_prerequisites,prerequisites>>. The following is an example `Restore` custom resource:
+
[,yaml]
----
 apiVersion: resources.cattle.io/v1
 kind: Restore
 metadata:
   name: restore-migration
 spec:
   backupFilename: backup-b0450532-cee1-4aa1-a881-f5f48a007b1c-2020-09-15T07-27-09Z.tar.gz
   encryptionConfigSecretName: encryptionconfig
   storageLocation:
     s3:
       credentialSecretName: s3-creds
       credentialSecretNamespace: default
       bucketName: rancher-backups
       folder: rancher
       region: us-west-2
       endpoint: s3.us-west-2.amazonaws.com
----
+
For help configuring the Restore, refer to the {xref-rancher-restore-config}[configuration reference] and to the {xref-back-restore-example-configs}[examples.]

. Apply the manifest to the cluster:
+
[,shell]
----
kubectl apply -f restore.yaml
----

*Result:* The backup file is created and updated to the target storage location. The resources are restored in this order:

. Custom Resource Definitions (CRDs)
. Cluster-scoped resources
. Namespaced resources

To check how the restore is progressing, you can check the logs of the `rancher-backup` operator Pod:

[,shell]
----
kubectl logs -n cattle-resources-system -l app.kubernetes.io/name=rancher-backup -f
----

You can also check the status of the `Restore` resource directly:
[,shell]
----
kubectl get restore restore-migration -o wide
----

[#_step_3_roll_back_to_a_previous_rancher_version]
== Step 3: Roll Back to a Previous Rancher Version

Rancher can be rolled back using the Helm CLI. To roll back to the previous version:

[,yaml]
----
helm rollback rancher -n cattle-system
----

If the previous revision is not the intended target, you can specify a revision to roll back to. To see the deployment history:

[,yaml]
----
helm history rancher -n cattle-system
----

When the target revision is determined, perform the rollback. This example will roll back to revision `3`:

[,yaml]
----
helm rollback rancher 3 -n cattle-system
----

[#_alternative_steps_for_special_scenarios]
== Alternative Steps for Special Scenarios

Alternative steps need to be performed for rollbacks in the following scenarios:

* Rolling back from v2.14.0 and later to an earlier version of v2.13.x.

In Rancher v2.13.0, Rancher Turtles became the default manager for CAPI resources, replacing the previously embedded cluster-api controllers, and in Rancher v2.14.0 the embedded cluster-api was removed entirely. As a result, if you roll back from Rancher v2.14.0 and later to an earlier version of Rancher v2.13.x and do not intend to continue using Rancher Turtles to manage CAPI resources, additional manual steps may be required to use the embedded cluster-api controllers. From Rancher v2.14.0 onward, Rancher Turtles is the only supported manager for CAPI resources.

In Rancher v2.14.0, the cluster-api module is upgraded from v1.10.6 to v1.12.2. The cluster-api v1.12.2, in turn, upgrades the apiVersions of its Custom Resource Definitions (CRDs) from `cluster.x-k8s.io/v1beta1` to `cluster.x-k8s.io/v1beta2`. Rancher backup files include Cluster API CRDs. When restoring backup data from Rancher v2.13.x to a local cluster after upgrading to v2.14.0, the Rancher Backup application first restores the v1beta1 CRDs. This fails because the v1beta2 version cannot be removed from the CRDs while v1beta2 custom resources are present in the cluster.

[IMPORTANT]
====
* Follow the instructions from this page for restoring Rancher on the same cluster where it was backed up from. In order to migrate Rancher to a new cluster, follow the steps to {xref-migrate-cluster}[migrate Rancher.]
* While restoring Rancher on the same setup, the Rancher deployment is manually scaled down before the restore starts, then the operator will scale it back up once the restore completes. As a result, Rancher and its UI will be unavailable until the restore is complete. While the UI is unavailable, use the original cluster kubeconfig with the restore YAML file: `kubectl create -f restore.yaml`.
====

[#_step_1_clean_up_the_upstream_local_cluster]
=== Step 1: Clean Up the Upstream (Local) Cluster

To avoid rollback failure, follow these https://github.com/rancher/rancher-cleanup/blob/main/README.md[instructions] to run the scripts *before* you attempt a restore operation or rollback:

* `cleanup.sh`: Cleans up the cluster.
* `verify.sh`:  Checks for any Rancher-related resources in the cluster.

[CAUTION]
====
There will be downtime while `cleanup.sh` runs, since the script deletes resources created by Rancher.
====

*Result:* All Rancher-related resources should be cleaned up on the upstream (local) cluster.
See the https://github.com/rancher/rancher-cleanup[rancher/rancher-cleanup repo] for more details and source code.

[#_step_2_restore_the_backup_and_bring_up_rancher]
=== Step 2: Restore the Backup and Bring Up Rancher

At this point, there should be no Rancher-related resources on the upstream cluster. Therefore, the next step will be the same as if you were migrating Rancher to a new cluster that contains no Rancher resources.
Follow these {xref-migrate-cluster}[instructions] to install the Rancher-Backup Helm chart and restore Rancher to its previous state.

Please keep in mind that:

. Step 3 can be skipped, because the Cert-Manager app should still exist on the upstream (local) cluster if it was installed before.
. At Step 4, install the Rancher version you intend to roll back to.
