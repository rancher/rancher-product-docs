If your organization uses Microsoft Active Directory Domain Services (AD DS) as a central user repository, you can configure {rancher-product-name} to communicate with an Active Directory (AD) server to authenticate users. This integration allows administrators to manage cluster and project access using externally defined Active Directory users and groups, while allowing users to sign in to the Rancher UI with their domain credentials.

Rancher uses LDAP to communicate with the Active Directory server. The authentication flow for Active Directory is therefore the same as for the {xref-openldap}[OpenLDAP authentication] integration.

[NOTE]
.External authentication concepts
====
Before you start, familiarize yourself with the concepts of {xref-authn-authz}#_external_authentication_configuration_and_principal_users[External Authentication Configuration and Principal Users].
====

[#_prerequisites]
== Prerequisites

You must create or obtain from your AD administrator a service account user for Rancher. This user must have sufficient permissions to perform LDAP searches and read attributes of users and groups under your AD domain.

* Usually a non-admin *Domain User* account suffices, as this user has read-only privileges for most objects in the domain partition by default.
* In locked-down AD configurations, this default behavior might not apply. In this case, ensure that the service account user has at least *Read* and *List Content* permissions granted either on the Base OU (enclosing users and groups) or globally for the domain.

[NOTE]
.Using TLS certificates
====
* If the certificate used by the Active Directory server is self-signed or not from a recognized certificate authority, have the CA certificate (concatenated with any intermediate certificates) in PEM format ready. Paste this certificate during configuration so that Rancher can validate the certificate chain.
* Authenticating via Rancher against Active Directory using TLS requires that certificates on the Active Directory server support Subject Alternative Name (SAN) attributes.
** If Common Name matching fails, the error received is `Error creating SSL connection: LDAP Result Code 200 "Network Error": x509: certificate relies on legacy Common Name field, use SANs or temporarily enable Common Name matching with GODEBUG=x509ignoreCN=0`.
** To resolve the error, update or replace the certificates on the Active Directory server with certificates that support SAN attributes. Alternatively, ignore this error by passing `GODEBUG=x509ignoreCN=0` as an environment variable to the Rancher server container.
====

[#_configuration_steps]
== Configuration Steps

[#_open_active_directory_configuration]
=== Open Active Directory Configuration

. Log in to the Rancher UI using the local `admin` account.
. In the top left corner, click *☰ > Users & Authentication*.
. In the left navigation menu, click *Auth Provider*.
. Click *ActiveDirectory*.
. Complete the configuration form. Refer to the parameter tables below for guidance.
. Click *Enable*.

[#_configure_active_directory_server_settings]
=== Configure Active Directory Server Settings

In the section titled `1. Configure an Active Directory server`, complete the fields with the information specific to your Active Directory deployment.

[NOTE]
.Determining search base values
====
If you are unsure about the correct values to enter in the user or group Search Base fields, see <<_annex_identify_search_base_and_schema_using_ldapsearch,Identify Search Base and Schema using ldapsearch>>.
====

[#tab-ad-server-parameters]
.AD Server parameters
[cols="1,3",options="header"]
|===
| Parameter | Description

| Hostname
| The host name or IP address of the Active Directory server.

| Port
| The port on which the Active Directory server listens for connections. Standard unencrypted LDAP uses port 389, while LDAPS uses port 636.

| TLS
| Enables LDAP over SSL/TLS (LDAPS).

| StartTLS
| Enables StartTLS on port 389.

| Server Connection Timeout
| The duration in seconds that Rancher waits before considering the Active Directory server unreachable.

| Service Account Username
| The user name of an Active Directory account with read-only access to your domain partition (see <<_prerequisites,Prerequisites>>). Enter the user name in NetBIOS format (such as `DOMAIN\serviceaccount`) or UPN format (such as `serviceaccount@example.com`).

| Service Account Password
| The password for the service account.

| Bind Mechanism
| Defines the authentication mechanism used to bind to Active Directory. Valid options are `simple` and `ntlm`. Default: `simple`. For details on requirements and channel binding tokens, see <<_bind_mechanisms>>.

| Default Login Domain
| The NetBIOS name of your Active Directory domain. When configured, user names entered without a domain prefix (such as `jdoe`) are automatically converted to a NetBIOS logon (`DOMAIN\jdoe`). This field is required when `Bind Mechanism` is set to `ntlm` and users log in with bare user names. If users authenticate with UPN format (`jdoe@example.com`) under simple bind, leave this field empty.

| User Search Base
| The Distinguished Name (DN) of the node in your directory tree from which to start searching for user objects. All users must be descendants of this base DN. For example: `ou=people,dc=example,dc=com`.

| Group Search Base
| The Distinguished Name (DN) under which groups reside, if different from the `User Search Base`. Otherwise, leave this field empty. For example: `ou=groups,dc=example,dc=com`.
|===

[#_bind_mechanisms]
=== Bind mechanisms

Rancher supports two bind mechanisms when communicating with Active Directory:

* *Simple bind (`simple`)*: The default mechanism. Authenticates credentials by sending the user name and password over the LDAP connection. TLS or StartTLS must be enabled to protect credentials in transit.
* *NTLM bind (`ntlm`)*: Authenticates using the NTLM protocol with a `tls-server-end-point` channel binding token (CBT). This satisfies environments enforcing LDAP channel binding and signing requirements.

[IMPORTANT]
.TLS or StartTLS required for NTLM bind
====
Setting `bindMechanism` to `ntlm` over an unencrypted LDAP connection causes Rancher to reject the configuration.

To use NTLM bind, enable either *TLS* (LDAPS on port 636) or *StartTLS* (port 389).
====

[NOTE]
.Domains with NTLM disabled
====
NTLM bind does not work in environments where Group Policy or security baselines disable NTLM authentication across the Active Directory domain. Support for Kerberos bind in NTLM-disabled environments is planned for a future release.
====

[#_supported_login_formats]
==== Supported login formats

The user name formats accepted by Rancher depend on the configured `bindMechanism`:

[#tab-ad-login-formats]
.Supported login formats by bind mechanism
[cols="2,1,1,3",options="header"]
|===
| Login format | `simple` | `ntlm` | Description

| `DOMAIN\user`
| Supported
| Supported
| Down-level logon format using the NetBIOS domain prefix.

| `user` (bare user name)
| Supported
| Supported*
| Bare user name without domain prefix. *Under `ntlm`, bare user names require `Default Login Domain` to be configured.

| `user@realm` (UPN)
| Supported
| Not supported
| User Principal Name (UPN) format. Under `ntlm`, UPN logins fail with an explicit error.
|===

[WARNING]
.Authentication disruption when downgrading Rancher
====
Downgrading Rancher from version 2.16 to an earlier version while `bindMechanism` is set to `ntlm` disables Active Directory authentication. Older versions do not recognize the `bindMechanism` field, ignore the parameter, and fall back to simple bind without channel binding tokens.

Before downgrading Rancher to a version earlier than 2.16, set `bindMechanism` back to `simple` in your Active Directory configuration and ensure that your domain controllers permit simple binds.
====

[#_configure_user_group_schema]
=== Configure User/Group Schema

In the section titled `2. Customize Schema`, map user and group attributes to match the schema used in your directory.

Rancher uses LDAP queries to search for and retrieve information about users and groups within Active Directory. The attribute mappings configured in this section construct search filters and resolve group memberships.

[NOTE]
.Identifying schema attributes
====
If you are unfamiliar with the schema used in your Active Directory domain, see <<_annex_identify_search_base_and_schema_using_ldapsearch,Identify Search Base and Schema using ldapsearch>> to determine the correct configuration values.
====

[#_user_schema]
==== User Schema

The table below details the parameters for the user schema configuration.

[#tab-user-schema-parameters]
.User schema configuration parameters
[cols="1,3",options="header"]
|===
| Parameter | Description

| Object Class
| The name of the object class used for user objects in your domain. Specify only the name of the object class without an LDAP filter wrapper (such as `person`).

| Username Attribute
| The user attribute whose value is suitable as a display name.

| Login Attribute
| The attribute whose value matches the user name entered during login. When users authenticate with their UPN (such as `jdoe@example.com`), set this field to `userPrincipalName`. For NetBIOS-style logon names (such as `jdoe`), set this to `sAMAccountName`.

| User Member Attribute
| The attribute containing the groups that a user is a member of.

| Search Attribute
| The attributes matched when searching for users in the UI. Separate multiple attributes with a pipe (`\|`) symbol. To match UPN user names, include `userPrincipalName`.

| Search Filter
| Filter applied when searching users to add to access lists, clusters, or projects. For example: `(\|(memberOf=CN=group1,CN=Users,DC=example,DC=com)(memberOf=CN=group2,CN=Users,DC=example,DC=com))`. If the filter does not use valid search syntax, user search results will be empty.

| User Enabled Attribute
| The attribute containing integer account flags used to determine whether an account is disabled. Leave this set to `userAccountControl`.

| Disabled Status Bitmask
| The bitmask value in `User Enabled Attribute` designating a disabled user account. Leave this set to the default value of `2`.
|===

[#_group_schema]
==== Group Schema

The table below details the parameters for the group schema configuration.

[#tab-group-schema-parameters]
.Group schema configuration parameters
[cols="1,3",options="header"]
|===
| Parameter | Description

| Object Class
| The name of the object class used for group objects in your domain. Specify only the name of the object class without an LDAP filter wrapper (such as `group`).

| Name Attribute
| The group attribute whose value is suitable for a display name.

| Group Member User Attribute
| The name of the user attribute whose format matches the group members in `Group Member Mapping Attribute`.

| Group Member Mapping Attribute
| The name of the group attribute containing group members.

| Search Attribute
| Attribute used to construct search filters when adding groups to clusters or projects.

| Search Filter
| Filter applied when searching groups to add to access lists, clusters, or projects. For example: `(\|(cn=group1)(cn=group2))`. If the filter does not use valid search syntax, group search results will be empty.

| Group DN Attribute
| The name of the group attribute whose format matches the values in the user attribute describing group memberships.

| Nested Group Membership
| Defines whether Rancher resolves nested group memberships. Avoid nested groups when possible to prevent performance degradation with large directory trees.
|===

[#_test_authentication]
=== Test Authentication

Test the connection to the Active Directory server using your Active Directory administrative account. When the test succeeds, authentication is enabled, and the account tested becomes a Rancher administrator.

[NOTE]
.Administrator account mapping
====
The Active Directory user used during this step maps to the local principal account and receives administrator privileges in Rancher. Choose this account carefully.
====

. Enter the *username* and *password* for the Active Directory administrative account.
. Click *Authenticate with Active Directory* to finish setup.

*Result:*

* Active Directory authentication is enabled.
* You are signed in to Rancher as an administrator using the tested Active Directory credentials.

[NOTE]
.Local administrator fallback
====
You can still log in using the locally configured `admin` account and password if directory services are disrupted.
====

[#_annex_identify_search_base_and_schema_using_ldapsearch]
== Annex: Identify Search Base and Schema using ldapsearch

The `ldapsearch` command-line utility queries your Active Directory server to determine schema attributes and hierarchy.

The following examples assume:

* Host name: `ad.example.com`
* Listening port: `389`
* Active Directory domain: `example`
* User credentials: user name `jdoe`, password `secret`

[#_identify_search_base]
=== Identify Search Base

Run `ldapsearch` to identify the Distinguished Name (DN) of the parent nodes for users and groups:

[,bash]
----
ldapsearch -x -D "example\jdoe" -w "secret" -p 389 \
  -h ad.example.com -b "dc=example,dc=com" -s sub "sAMAccountName=jdoe"
----

This command performs an LDAP search with the search base set to the domain root (`-b "dc=example,dc=com"`) and returns attributes for the user:

image::ldapsearch-user.png[LDAP search output displaying user distinguished name, 600]

If the user DN is `CN=John Doe,CN=Users,DC=example,DC=com`, configure *User Search Base* with `CN=Users,DC=example,DC=com`.

Based on the DN of the group referenced in the `memberOf` attribute, configure *Group Search Base* with `OU=Groups,DC=example,DC=com`.

[#_identify_user_schema]
=== Identify User Schema

The query output determines the values for the user schema:

* `Object Class`: *person*
* `Username Attribute`: *name*
* `Login Attribute`: *sAMAccountName*
* `User Member Attribute`: *memberOf*

[NOTE]
.UPN login attribute
====
If users authenticate with their UPN (such as `jdoe@example.com`) under simple bind, set `Login Attribute` to *userPrincipalName*.
====

Set `Search Attribute` to `sAMAccountName|name` so users can be located by user name or display name.

[#_identify_group_schema]
=== Identify Group Schema

Query one of the groups associated with this user (such as `CN=examplegroup,OU=Groups,DC=example,DC=com`):

[source,bash]
----
ldapsearch -x -D "example\jdoe" -w "secret" -p 389 \
  -h ad.example.com -b "ou=groups,dc=example,dc=com" \
  -s sub "CN=examplegroup"
----

The output displays attributes for group objects:

image::ldapsearch-group.png[LDAP search output displaying group attributes, 600]

Use these values in the group schema configuration:

* `Object Class`: *group*
* `Name Attribute`: *name*
* `Group Member Mapping Attribute`: *member*
* `Search Attribute`: *sAMAccountName*

The `member` attribute contains the DN of the referenced user, which corresponds to `distinguishedName` in the user object. Set `Group Member User Attribute` to `distinguishedName`.

The `memberOf` attribute in the user object matches the `distinguishedName` of the group. Set `Group DN Attribute` to `distinguishedName`.

[#_annex_troubleshooting]
== Annex: Troubleshooting

If you experience issues while testing the connection to the Active Directory server, first verify the service account credentials and search base configuration. You can also inspect Rancher server debug logs for additional diagnostic details. For more information, see xref:faq/technical-items.adoc#_how_can_i_enable_debug_logging[How can I enable debug logging].

[#_troubleshoot_channel_binding_failures]
=== LDAP channel binding failures (data 80090346)

When Active Directory enforces LDAP channel binding and Rancher uses `bindMechanism: ntlm`, authentication can fail with LDAP error code `49` (`invalidCredentials`) and Windows subcode `80090346` (`SEC_E_BAD_BINDINGS`):

[source,console]
----
LDAP Result Code 49 "Invalid Credentials": 80090346: LdapErr: DSID-0C09056B, comment: AcceptSecurityContext error, data 80090346, v4563
----

The error `SEC_E_BAD_BINDINGS` indicates that the channel binding token (CBT) calculated from the TLS session does not match the token expected by the domain controller.

Review the following common causes and remediations:

TLS inspection or proxy termination::
The `tls-server-end-point` channel binding token is computed from the TLS certificate presented by the Active Directory server. If an intermediate proxy, load balancer, or firewall performs SSL/TLS termination or certificate inspection between Rancher and the domain controller, the certificate hash differs from the certificate on the domain controller.
+
*Remediation:* Configure intermediate proxies and load balancers to use TCP pass-through (Layer 4) for LDAPS traffic, allowing Rancher to establish a direct TLS session with the domain controller.

Missing or incomplete CA certificate chain::
If the certificate authority (CA) that issued the domain controller certificate is missing or incomplete in Rancher, certificate validation fails or binds to an unverified endpoint.
+
*Remediation:* Verify that the complete CA certificate chain (including root and any intermediate certificates) is provided in the *Certificate* field during Active Directory configuration.

UPN login format used with NTLM::
Users who attempt to authenticate with their User Principal Name (`user@example.com`) receive an authentication error when `bindMechanism` is set to `ntlm`.
+
*Remediation:* Instruct users to log in using the `DOMAIN\user` format, or configure *Default Login Domain* and have users log in with their bare user name.
