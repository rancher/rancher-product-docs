[#_monitoring_dashboards]
== Rancher Monitoring Dashboards

[IMPORTANT]
====
Starting in Rancher v2.15.0, new monitoring installations use the decoupled `rancher-monitoring-dashboards` chart.

Rancher maintains the legacy `rancher-monitoring` chart to support existing deployments, but it does not receive new updates. Use the `rancher-monitoring-dashboards` chart for ongoing updates and support.
====

The `rancher-monitoring-dashboards` chart provides Grafana dashboards and Rancher UI integration for external Prometheus monitoring stacks, such as `kube-prometheus-stack`.

* *No bundled runtime:* Operates without depending on Rancher-shipped `kube-prometheus-stack` images or components. It operates independently and does not require installing the legacy `rancher-monitoring` chart. It installs a dashboard-only version of `rancher-monitoring`.
* *Prerequisites:* Requires uninstalling the `rancher-monitoring` chart and using a Prometheus infrastructure. Although several configurations are supported, installing `kube-prometheus-stack` is the simplest method.

[#_migrating_from_rancher-monitoring_to_rancher_monitoring_dashboards]
=== Migrating from `rancher-monitoring` to `rancher-monitoring-dashboards`

Follow these steps to migrate to `rancher-monitoring-dashboards`: 

. Uninstall the `rancher-monitoring` chart. See {xref-monitoring-uninstall}[].
. Install your own `kube-prometheus-stack`. See <<_install_kube_prometheus_stack_chart>>.
. Install `rancher-monitoring-dashboards`. See <<_install_rancher_monitoring_dashboards_chart>>.

If you need to preserve or migrate existing data, refer to the official Grafana and Prometheus documentation:

* https://grafana.com/docs/grafana/latest/administration/back-up-grafana/[Grafana | Back up Grafana]
* https://prometheus.io/docs/prometheus/latest/querying/api/#snapshot[Prometheus | TSDB Admin APIs - Snapshot]
* https://prometheus.io/docs/prometheus/latest/storage/[Prometheus | Storage]

=== Rancher Monitoring Dashboards Installation

This section guides you through setting up your Prometheus stack and installing the `rancher-monitoring-dashboards` chart.

[#_install_kube_prometheus_stack_chart]
==== Install `kube-prometheus-stack` chart

Before installing the `rancher-monitoring-dashboards` chart, you must first set up the underlying monitoring infrastructure using the https://github.com/prometheus-community/helm-charts/tree/main/charts/kube-prometheus-stack[`kube-prometheus-stack`] chart:

. Add the https://github.com/prometheus-community/helm-charts[prometheus-community] Helm repository to access the `kube-prometheus-stack` chart. You can do this through the Rancher UI or using the Helm CLI with the following command.
+
[tabs,sync-group-id=UIorHelm CLI]
======
UI::
+
--

. Select *☰ > Cluster Management*.
. Locate your cluster and click *Explore*.
. In the left navigation menu, select *Apps > Repositories*.
. Click *Add Repository*.
. Enter a *Name* (such as `prometheus-community`).
. In the *Index URL* field, enter `https://prometheus-community.github.io/helm-charts`.
. Click *Add Repository*.

--

Helm::
+
--

[,shell]
----
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update
----

--
======
+
*Result:* The `prometheus-community` Helm repository is added and available for chart installations.

. Create the `kube-prometheus-stack` `values.yaml` file. Configure the file with the following required settings to ensure `kube-prometheus-stack` integrates properly and supports embedded dashboards in `rancher-monitoring-dashboards`.
+
[,yaml]
----
grafana:
  # NOTE: Do NOT set root_url or serve_from_sub_path here
  grafana.ini:
    security:
      allow_embedding: true
    auth:
      disable_login_form: false
    auth.anonymous:
      enabled: true
      org_role: Viewer
    dashboards:
      default_home_dashboard_path: /tmp/dashboards/rancher-default-home.json
    users:
      auto_assign_org_role: Viewer

# Prometheus configuration to pick up all ServiceMonitors
prometheus:
  prometheusSpec:
    serviceMonitorSelectorNilUsesHelmValues: false
    podMonitorSelectorNilUsesHelmValues: false

# No metric exporter by default
kubeEtcd:
  enabled: false
kubeControllerManager:
  enabled: false
kubeScheduler:
  enabled: false
kubeProxy:
  enabled: false
----
+
[IMPORTANT]
====
By default, the rancher-monitoring-dashboards chart does not enable metric scraping for `kubeEtcd`, `kubeControllerManager`, `kubeScheduler`, or `kubeProxy`. To export metrics from these components, you must configure https://github.com/prometheus-community/PushProx[PushProx].
====

. Install the `kube-prometheus-stack` chart in the `cattle-monitoring-system` namespace through the Rancher UI or via the Helm CLI, applying the `values.yaml` file from the previous step:
+
[tabs,sync-group-id=UIorHelm CLI]
======
UI::
+
--

. Select *☰ > Cluster Management*.
. Locate your cluster and click *Explore*.
. In the left navigation menu, select *Apps > Charts*.
. Locate and select the *kube-prometheus-stack* chart.
. Click *Install this version*.
. In the *Namespace* dropdown, select *cattle-monitoring-system*. If the namespace does not exist:
.. Select *Create a New Namespace* and enter `cattle-monitoring-system`.
.. Enter a unique *Name*.
.. Select *Customize Helm options before install*.
. Click *Next*.
. Select *Edit YAML* and paste or upload your `values.yaml` file.
. Click *Next*.
. Select and specify additional deployment options.
. Click *Install*.

--

Helm::
+
--

[,shell]
----
helm install kube-prometheus-stack prometheus-community/kube-prometheus-stack \
  --namespace cattle-monitoring-system \
  --create-namespace \
  --debug \
  --wait \
  -f values.yaml
----

--
======
+
*Result:* The Prometheus monitoring infrastructure is deployed in the `cattle-monitoring-system` namespace.

=== Rancher Monitoring Dashboards Installation

This section guides you through setting up your Prometheus stack and installing the `rancher-monitoring-dashboards` chart using the xref:integrations/fleet/appco.adoc[SUSE Application Collection (AppCo)].

[#_create_the_appco_credentials]
==== Create the AppCo credentials

First create the secret that will be used by Kubernetes to pull the images and login to Helm to pull the required chart from SUSE AppCo. The secret needs to be created in the `cattle-monitoring-system` namespace where the chart is installed.

Run the following commands to create the secret:

[,shell]
----
kubectl create namespace cattle-monitoring-system

kubectl create secret docker-registry application-collection --docker-server=dp.apps.rancher.io --docker-username=<your_username> --docker-password=<your_password> --namespace cattle-monitoring-system
----

Run the following command to login to Helm, replacing `<your_username>` and `<your_password>` with your SUSE AppCo credentials:

[,shell]
----
helm registry login dp.apps.rancher.io -u <your_username> -p <your_password>
----

[#_customization_and_overrides]
=== Customization and Overrides

Use the configuration settings in this section to customize the `rancher-monitoring-dashboards` chart for your environment. 

* Override default proxy images. See <<_monitoring_proxy_image_customization>>.
* Align upstream service names with your Prometheus stack and disable unused K3s components. See <<_service_name_overrides>>.

[#_monitoring_proxy_image_customization]
==== Monitoring Proxy Image Customization

A single NGINX pod (`monitoringProxy`) acts as a proxy for Grafana, Prometheus, and Alertmanager, ensuring the Kubernetes API server’s service proxy (used by the Rancher UI) can reach them reliably. You can customize the NGINX image using the following configuration:

[,yaml]
----
monitoringProxy:
  image:
    repository: <new/image>
    tag: <version>
----

[#_service_name_overrides]
==== Service Name Overrides

The default `values.yaml` assumes standard service naming conventions (for example, kube-prometheus-stack-<application>), as shown below:

[,yaml]
----
grafanaProxy:
  upstreamService: kube-prometheus-stack-grafana

prometheusProxy:
  upstreamService: kube-prometheus-stack-prometheus

alertmanagerProxy:
  upstreamService: kube-prometheus-stack-alertmanager
----

This creates mirror services alongside the new chart, which the reverse proxy uses to enable Rancher UI functionality. If you modified the service names during installation, update the `upstreamService` configuration accordingly:

[,yaml]
----
grafanaProxy:
  upstreamService: <upstream_service_name>

prometheusProxy:
  upstreamService: <upstream_service_name>

alertmanagerProxy:
  upstreamService: <upstream_service_name>
----

[NOTE]
====
Make sure to disable `k3sServer` if you are not using K3s:

[,yaml]
----
k3sServer:
  enabled: false
----
====

[#_faq]
=== FAQ

*Q*: What is the new chart being introduced?

*A*: The `rancher-monitoring-dashboards` chart includes only dashboard artifacts and Rancher UI integration metadata. It does not include Prometheus, Grafana, Alertmanager, exporters, or PushProx. To deploy a full monitoring runtime, install `kube-prometheus-stack` separately from the Prometheus Community Helm repository.

*Q*: Will the legacy `rancher-monitoring` chart still be available?

*A*: Yes. Rancher v2.15 retains the Rancher v2.14 version of the `rancher-monitoring` chart, but you cannot install it directly as a new installation. Rancher v2.15 also includes an updated monitoring version available exclusively for upgrades.

*Q*: What happens to existing installations when upgrading to Rancher v2.15?

*A*: You can upgrade existing installations to the updated monitoring release in Rancher v2.15. To migrate fully to the new dashboards-only chart, follow the standard upstream migration path for Prometheus and Grafana.

*Q*: How does the Rancher UI locate Grafana and Prometheus?

*A*: In this release, monitoring service URLs (such as `rancher-monitoring-<service>`) remain hardcoded in the Rancher UI. Support for configurable, user-provided URLs is planned for a future release.

*Q*: How does the Rancher UI monitoring installation workflow change?

*A*: The Rancher UI installation workflow uses `kube-prometheus-stack` for runtime configuration options. The `rancher-monitoring-dashboards` chart exposes values only for dashboards and Rancher UI integration.

[#_rancher_monitoring]
== Rancher Monitoring

[IMPORTANT]
====
The `rancher-monitoring` chart is no longer available in the UI for new installs, but it remains fully supported to upgrade existing `rancher-monitoring` deployments.
====

The `rancher-monitoring` application can quickly deploy leading open-source monitoring and alerting solutions onto your cluster.

Introduced in Rancher v2.5, the application is powered by https://prometheus.io/[Prometheus], https://grafana.com/grafana/[Grafana],  https://prometheus.io/docs/alerting/latest/alertmanager/[Alertmanager], the https://github.com/prometheus-operator/prometheus-operator[Prometheus Operator], and the https://github.com/DirectXMan12/k8s-prometheus-adapter[Prometheus adapter.]

For information on V1 monitoring and alerting, available in Rancher v2.2 up to v2.4, please see the Rancher v2.0--v2.4 docs on xref:[cluster monitoring], xref:[alerting], xref:[notifiers] and other xref:[tools].

Using the `rancher-monitoring` application, you can quickly deploy leading open-source monitoring and alerting solutions onto your cluster.

[#_features]
=== Features

Prometheus lets you view metrics from your Rancher and Kubernetes objects. Using timestamps, Prometheus lets you query and view these metrics in easy-to-read graphs and visuals, either through the Rancher UI or Grafana, which is an analytics viewing platform deployed along with Prometheus.

By viewing data that Prometheus scrapes from your cluster control plane, nodes, and deployments, you can stay on top of everything happening in your cluster. You can then use these analytics to better run your organization: stop system emergencies before they start, develop maintenance strategies, or restore crashed servers.

The monitoring application:

* Monitors the state and processes of your cluster nodes, Kubernetes components, and software deployments.
* Defines alerts based on metrics collected via Prometheus.
* Creates custom Grafana dashboards.
* Configures alert-based notifications via email, Slack, PagerDuty, etc. using Prometheus Alertmanager.
* Defines precomputed, frequently needed or computationally expensive expressions as new time series based on metrics collected via Prometheus.
* Exposes collected metrics from Prometheus to the Kubernetes Custom Metrics API via Prometheus Adapter for use in HPA.

See {xref-how-monitoring-works}[How Monitoring Works] for an explanation of how the monitoring components work together.

[#_deploying_prometheus_federator_with_suse_application_collection]
=== Deploying Prometheus Federator with SUSE Application Collection

[IMPORTANT]
====
* **Mandatory Image Configuration:** Default component images (Grafana, Prometheus, Alertmanager, etc.) are no longer provided by the chart. You must explicitly supply image repositories and tags in your configuration.
* The `chartSource.repo` URL must point strictly to the repository root directory, do not append `/index.yaml` to the URL: +https://raw.githubusercontent.com/rancher/ob-team-charts/refs/heads/main+.
* Ensure you create the AppCo secret in the namespace `cattle-project-<project_id>-monitoring` and note this must be done for all projects. Include the `imagePullSecrets` in your `values.yaml` file to pull images from the SUSE AppCo registry:
+
[,yaml]
----
helmProjectOperator:
  valuesOverride:
    global:
      imagePullSecrets:
        - name: application-collection
    grafana:
      imagePullSecrets:
        - name: application-collection
----
====

If installing using the UI ensure all required fields under the **Project Monitoring Chart** and **Grafana Chart** tabs are filled respective to your `values.yaml` configuration, note the example UI view below. This changes the **images**, not the chart. At the moment it is not possible to choose what version of the Grafana chart is installed.

image::UI-prometheus-example.png[UI Prometheus Charts Example]

To supply the required Prometheus, Grafana, and Alertmanager images via Helm, specify them under `helmProjectOperator.valuesOverride` when deploying Prometheus Federator. [#_pushprox_alternative_using_prometheus_agent]
=== Pushprox alternative using Prometheus Agent

Previous versions of `rancher-monitoring` relied on a Rancher-maintained fork of PushProx to scrape metrics from components that bind exclusively to port `127.0.0.1`. These components include:

* `kube-proxy`
* `etcd`
* `kube-scheduler`
* `kube-controller-manager`

This localhost binding strategy is standard across Kubernetes distributions, including K3s and RKE2, and aligns with CIS benchmark recommendations. Upstream PushProx lacks the custom features present in the Rancher fork, making it an unsuitable replacement.

Note that authentication behavior varies across components:

* `kube-scheduler` and `kube-controller-manager` require a valid bearer token for scrape requests.
* `kube-proxy` and `etcd` do not enforce authentication, which remains secure because scrape requests operate entirely over the local loopback interface.

To collect these local metrics, deploy a Prometheus Agent on each control-plane node. The agent scrapes all four targets over loopback and forwards the collected metrics to the primary Prometheus instance via `remote_write`. This approach avoids creating new listening ports or exposing control-plane network interfaces, offering a safer alternative to tools like `socat`.

. First enable `remote-write` on the previously installed `kube-prometheus-stack chart`:
+
[,shell]
----
helm upgrade kube-prometheus-stack oci://dp.apps.rancher.io/charts/prometheus-operator \
    -n cattle-monitoring-system --reuse-values \
    --set prometheus.prometheusSpec.enableRemoteWriteReceiver=true \
    --wait
----

. Create the service that the Prometheus Agent will use to send metrics to the main Prometheus instance:
+
[,shell]
----
apiVersion: v1
kind: Service
metadata:
  name: kube-prometheus-stack-prom-prometheus-write
  namespace: cattle-monitoring-system
spec:
  selector:
    app.kubernetes.io/name: prometheus
    operator.prometheus.io/name: kube-prometheus-stack-prom-prometheus
  ports:
    - name: remote-write
      port: 9091
      targetPort: 9091
----

. Create the CRD for the Prometheus Agent:
+
[,shell]
----
apiVersion: monitoring.coreos.com/v1alpha1
kind: PrometheusAgent
metadata:
  name: control-plane-agent
  namespace: cattle-monitoring-system
spec:
  replicas: <number_of_replicas>
  hostNetwork: true
  listenLocal: true
  serviceAccountName: kube-prometheus-stack-prom-prometheus
  nodeSelector:
    node-role.kubernetes.io/control-plane: "true"
  tolerations:
    - operator: Exists
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchLabels:
              app.kubernetes.io/name: prometheus-agent
              operator.prometheus.io/name: control-plane-agent
          topologyKey: kubernetes.io/hostname
  scrapeConfigSelector:
    matchLabels:
      control-plane-agent: "true"
  remoteWrite:
    - url: https://kube-prometheus-stack-prom-prometheus-write.cattle-monitoring-system.svc:9091/api/v1/write
      authorization:
        type: Bearer
        credentialsFile: /var/run/secrets/kubernetes.io/serviceaccount/token
      tlsConfig:
        insecureSkipVerify: true
----

. Create the `ScrapeConfig` that matches the `scrapeConfigSelector` above:
+
[,shell]
----
apiVersion: monitoring.coreos.com/v1alpha1
kind: ScrapeConfig
metadata:
  name: control-plane-agent-kube-proxy
  namespace: cattle-monitoring-system
  labels:
    control-plane-agent: "true"
spec:
  jobName: kube-proxy
  staticConfigs:
    - targets: ["127.0.0.1:10249"]
---
apiVersion: monitoring.coreos.com/v1alpha1
kind: ScrapeConfig
metadata:
  name: control-plane-agent-kube-etcd
  namespace: cattle-monitoring-system
  labels:
    control-plane-agent: "true"
spec:
  jobName: kube-etcd
  staticConfigs:
    - targets: ["127.0.0.1:2381"]
---
apiVersion: monitoring.coreos.com/v1alpha1
kind: ScrapeConfig
metadata:
  name: control-plane-agent-kube-scheduler
  namespace: cattle-monitoring-system
  labels:
    control-plane-agent: "true"
spec:
  jobName: kube-scheduler
  scheme: HTTPS
  tlsConfig:
    insecureSkipVerify: true
  authorization:
    credentials:
      name: kube-prometheus-stack-prom-prometheus-token
      key: token
  staticConfigs:
    - targets: ["127.0.0.1:10259"]
---
apiVersion: monitoring.coreos.com/v1alpha1
kind: ScrapeConfig
metadata:
  name: control-plane-agent-kube-controller-manager
  namespace: cattle-monitoring-system
  labels:
    control-plane-agent: "true"
spec:
  jobName: kube-controller-manager
  scheme: HTTPS
  tlsConfig:
    insecureSkipVerify: true
  authorization:
    credentials:
      name: kube-prometheus-stack-prom-prometheus-token
      key: token
  staticConfigs:
    - targets: ["127.0.0.1:10257"]
----

At this point, the Prometheus Agent is fully configured to scrape metrics from the control-plane components and forward them to the existing Prometheus instance.

[#_optional_security_hardening]
==== Optional Security Hardening

Prometheus' `remote_write` receiver (`--web.enable-remote-write-receiver`) lacks built-in authentication capabilities, and `prometheus-operator` does not currently provide a CRD field to configure receiver authentication. For more details on this limitation, refer to the https://github.com/prometheus-operator/prometheus-operator/issues/4200[upstream prometheus-operator issue].

Leaving the receiver unauthenticated exposes the endpoint and increases the cluster's attack surface. To mitigate this risk, deploy `kube-rbac-proxy` as a sidecar container to enforce RBAC authentication and authorization in front of the `remote_write` receiver.

. First create the `configmap` that will hold the configuration file for the proxy:
+
[,shell]
----
 kubectl create configmap kube-rbac-proxy-remote-write-config \
   -n cattle-monitoring-system \
   --from-literal=config-file.yaml='authorization:
   resourceAttributes:
     namespace: cattle-monitoring-system
     apiVersion: v1
     resource: services
     subresource: remote-write
     name: kube-prometheus-stack-prom-prometheus-write'
----

. Give the appropriate permissions to the `serviceAccount`:
+
[,shell]
----
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: kube-prometheus-stack-prom-prometheus-auth-delegator
subjects:
  - kind: ServiceAccount
    name: kube-prometheus-stack-prom-prometheus
    namespace: cattle-monitoring-system
roleRef:
  kind: ClusterRole
  name: system:auth-delegator
  apiGroup: rbac.authorization.k8s.io
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: control-plane-agent-remote-write
rules:
  - apiGroups: [""]
    resources: ["services/remote-write"]
    resourceNames: ["kube-prometheus-stack-prom-prometheus-write"]
    verbs: ["create"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: control-plane-agent-remote-write
subjects:
  - kind: ServiceAccount
    name: kube-prometheus-stack-prom-prometheus
    namespace: cattle-monitoring-system
roleRef:
  kind: ClusterRole
  name: control-plane-agent-remote-write
  apiGroup: rbac.authorization.k8s.io
----

. Lastly, in the `kube-prometheus-stack` chart, under `prometheus.PrometheusSpec.containers` add the following:
+
[,yaml]
----
 containers:
   - name: kube-rbac-proxy-remote-write
     image: dp.apps.rancher.io/containers/kube-rbac-proxy:0.23.0  
     args:
       - --secure-listen-address=0.0.0.0:9091
       - --upstream=http://127.0.0.1:9090/
       - --config-file=/etc/kube-rbac-proxy/config-file.yaml
       - --logtostderr=true
       - --v=2
     ports:
       - containerPort: 9091
         name: remote-write
     volumeMounts:
       - name: kube-rbac-proxy-config
         mountPath: /etc/kube-rbac-proxy
     resources:
       requests: { cpu: 10m, memory: 32Mi }
       limits: { cpu: 100m, memory: 64Mi }
 volumes:
   - name: kube-rbac-proxy-config
     configMap:
       name: kube-rbac-proxy-remote-write-config
----
+
[IMPORTANT]
====

* Port numbers 10249, 10257, 10259, 2381, node role labels, and whether kube-proxy is loopback-bound can differ by distribution and Kubernetes version. Check with `ss -tln` on a node directly before using the configuration outside of K3s or RKE2.

* Resources requests and limits are examples and should be configured based on the cluster size and workload requirements.
====

endif::[]

=== Built-in Dashboards

By default, the monitoring application deploys Grafana dashboards (curated by the https://github.com/prometheus-operator/kube-prometheus[kube-prometheus] project) onto a cluster.

It also deploys an Alertmanager UI and a Prometheus UI. For more information about these tools, see {xref-monitoring-builtin-dashboards}[Built-in Dashboards.]

[#_default_metrics_exporters]
=== Default Metrics Exporters

By default, Rancher Monitoring deploys exporters (such as https://github.com/prometheus/node_exporter[node-exporter] and https://github.com/kubernetes/kube-state-metrics[kube-state-metrics]).

These default exporters automatically scrape metrics for CPU and memory from all components of your Kubernetes cluster, including your workloads.

[#_known_issues]
== Known Issues

There is a https://github.com/rancher/rancher/issues/28787#issuecomment-693611821[known issue] that K3s clusters require more than the allotted default memory. If you enable monitoring on a K3s cluster, set `prometheus.prometheusSpec.resources.memory.limit` to 2500 Mi and `prometheus.prometheusSpec.resources.memory.request` to 1750 Mi.

See {xref-monitoring-debug-high-memory}[Debugging High Memory Usage] for advice and recommendations.
